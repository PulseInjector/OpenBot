# aooo bot stage two implementation plan

> This file is the project plan's only copy, maintained in this repository. The original Notion page
> has been removed and nothing is maintained there.

## Overall goal and scope

Stage two delivers aooo bot on the macOS desktop and in the browser. The user creates a Bot in conversation, grants it tools, and lets it do real work. Schedules and events keep the Bot on an existing duty. After human handling, a process crash, or a user redirect, the Bot resumes under explicit rules. The Bot can also delegate, and use memory and skills. Product data can be backed up and restored in an isolated environment. While the project advances, it completes the remaining 21 interview questions and corrects 5 existing answers as the related features land.

Development follows the full-fork route. It keeps OpenBOT's Agent, tool loop, business queues, UI, and existing business models. The main additions are the local runtime and history, safe recovery, and persistent mid-run additions, plus the wiring and narrow patches those require. Existing collaboration, memory, and skills are adapted, regression-tested, and actually reused rather than rebuilt. The scope does not grow to a new workflow platform, a full remote inspector, transparent recovery of arbitrary remote processes, lossless migration of old cloud history, Windows or mobile, or production-scale performance promises. Old cloud threads keep their original ownership; this stage starts from newly created local threads.

**Starting point.** The read-only code review on 2026-11-12 is this repository's starting point, with HEAD `3592f850eff49204d0f2b46a905d38f2627f2d81` and no tracked-file changes. This document is an implementation plan; the features below are not yet implemented and the product tests have not been rerun. Install, build, database, and partial test records exist from November 1, but at that time the full chain of a real model, external applications, and the native desktop had not passed acceptance, and one server test failed. The steps below therefore start by building a real working version, and do not treat the architecture draft's success tone as the current state.

**Business scenario.** A project-tracking Bot reads project release notes and user-supplied material, and updates an authorized Notion work page with sourced compatibility changes. New material, scheduled checks, or GitHub repository events push the same duty forward. When needed, an upgrade-assessment Bot gives advice; the project-tracking Bot decides the final document content. Notion is fixed as the target because the repository already has read and write access for it. The Google Drive adapter is read-only, and Lark has no adapter in the checked-out code, so no new connector is added for the first business chain.

**How the work runs.** Advance in the table's order. Each segment implements the feature, accepts the real result, then completes the assigned question's full answer. Each remaining question is assigned exactly once, and its answer cites that segment's commits, tests, and real artifacts. Segment 1 already accepts business results and collects the needed data. Segment 9 assembles the complete assessment.

This file is the only master plan for the work that follows. It replaces the old question list's ordering and completion standard. When an implementation changes a mechanism, update only the affected part. The old dependency review is not a daily checklist, and the old four-week budget does not carry over. Interview questions, answers, and personal narratives are kept in a personal notes vault, not in this file.

## 1. A real workbench that survives reopen

### Segment goal

Local mode starts with no Intelligence configuration. The user creates a Bot in conversation, the Bot reads material, updates a Notion work page, and reads the result back. Closing the page during a run does not cancel the server's work. Reopening shows the history, status, and artifacts. After a lost creation response or a partial grant failure, the original request continues. This is the first version that is actually usable.

### Implementation steps

1. **Fix the development and real-call environment.** Build the `aooo/main` integration branch from the commit named above, keeping the current untracked files. Install per [package.json](../../package.json) using the locked Bun version and the lockfile. Check PostgreSQL, Docker, Rust and Cargo, model configuration, and the computer services; re-check the gaps from November 1 instead of trusting the old record. Adapt the local startup branch along [scripts/start.sh](../../scripts/start.sh) with its own ports and database. Prepare one real model, one Notion test page, and two fixed material batches. The second batch contains a new compatibility change, unrelated changes, and a duplicate source. Keep an initial copy of the page that states the required facts, the sources, and the do-not-touch area up front. Fill in missing real credentials through the existing configuration and connection UI. A fake model or a local file cannot substitute for this segment's real-application acceptance.

2. **Pick one runtime backend, keep the existing Agent.** Add explicit local and intelligence mode configuration in [config.ts](../../server/src/config.ts). Local mode uses a custom persistent runner and SSE. One runtime never receives `intelligence` together with a custom `runner`. Stay on locked versions; do not upgrade dependencies first. Change the assembly in [mountCopilotRuntime](../../server/src/copilot.ts), keeping `agentFor`, tool selection, and the existing model loop. The new runtime modules go under `server/src/local-runtime/`, split into `store`, `coordinator`, `runner`, and `routes`. This plan requires those modules; they are not existing capability. Regular skills and memory keep their local paths. Remote learning is explicitly unavailable in local mode for now, and segment 7 delivers the full local replacement. Also change the desktop startup validation and the env branches so the dev build can select the local service. Signing and packaging come in segment 8.

3. **Wire persistence directly into the first work chain.** Add `runtime.ts` in [the database schema directory](../../server/src/db/schema), wired through the existing schema export, the migration log, and [migrate.ts](../../server/scripts/migrate.ts). Use the record duties in the table below. Existing business tables, thread IDs, approvals, and queue IDs are not rebuilt. Events are the record of fact. Messages and state are rebuildable read projections. There are never two independent histories.

   | Record | What this segment must settle and implement |
   |---|---|
   | Local thread binding | The existing thread ID, Bot, ownership link, history version, and current execution generation. Access follows the existing user and session authorization. Being able to use a Bot does not mean being able to read any thread. |
   | Work run `run` | Stable run ID, initiator and trigger source, request deduplication key, business reference, state, artifact reference. The server creates the record for manual work. Later background runs attach to the original business run. |
   | Execution attempt `attempt` | Run ID, attempt ID, execution generation, holder, lease expiry, current state, and end reason. A retry does not create new business work. |
   | Ordered events and the message projection | An increasing sequence inside the thread, the attempt, message IDs, tool calls and their results, and state and activity events. `(threadId, seq)` is unique. Events reach clients only after commit. |
   | Tool operation `operation` | Operation ID, attempt, toolCallId, tool and target, actual parameters and digest, executing identity, dispatch flag, and the result or an unknown state. Build intent only from complete parameters. Save the dispatch flag before the call. Save the result before handing it back to the model. |

   The minimal coordination interface is submit, connect, and stop a run, read history, and execute at tool boundaries. The HTTP adapter authenticates and creates a trusted submission, saving the current actor, thread, Bot, business source, and request key. The submission passes through the server request context to the coordinator, which fixes it into the attempt. A client cannot name a trusted identity, and identity is never passed through a global thread-to-actor map. Background work enters through the same service's trusted internal submission path. A submission is deduplicated inside a transaction and takes the thread's execution right. The coordinator then reads the authoritative history, merges the new input, and creates the attempt. A client cannot overwrite server history with an old full messages array; reuse the message-ID diffing approach of [turnMessages](../../toolkit/src/run-turn.ts). Leases and execution generations use conditional updates, so an expired executor cannot advance current history or start a new tool. Crashed work is not replayed automatically in this segment. It shows as interrupted or pending, and segment 4 delivers the full recovery behavior.

4. **Implement authentication, execution, and observation separately.** Before the [runtime mount point](../../server/src/app.ts), check login state, Bot access, and thread ownership for every run, connect, stop, and history request. The existing policy gate does not replace these checks. SSE `runner.run` takes no trusted user identity parameter, so this run's actor comes from the submission context saved in the previous step. It is never inferred from the thread owner. Read, run, and stop are each authorized under the existing session-member and Bot-access rules. Keep the mint and read entries of [thread-routes.ts](../../server/src/channels/thread-routes.ts). The product history endpoint switches to identity-carrying async database reads, and unused admin endpoints stay off by default.

   The server executes the work; the browser subscribes to results. connect first registers the observation and buffers live events, then reads a consistent snapshot with its event sequence. After the replay, the client deduplicates and continues by message ID and sequence. The database event table is the final cross-process record. Notifications only wake a catch-up read. When a notification is lost, polling by sequence continues.

   An attempt saves owner, lease, controlVersion, and stopRequested. The executor checks these fields before every tool call and periodically during a run. A stop request binds the run and the attempt in one transaction. A stopped report is sent only after a persistent terminal state holds. An old request cannot end a new attempt. Change [channel-chat.tsx](../../app/src/components/channels/channel-chat.tsx) and [bot-thread.ts](../../app/src/lib/copilot/bot-thread.ts) so the original conversation shows the run state, the failure reason, and the artifacts.

5. **Record operations at the real tool boundary, and prove the run can stop there.** Reuse one operation wrapper at the [built-in tool execute wrapper](../../server/src/copilot.ts) and [headless-tools](../../toolkit/src/headless-tools.ts), in this order: re-check the execution right and permissions, record the intent, execute, persist the result, return to the model. Server plugins and computer calls still pass through the original authorization and audit. Tools with side effects prefer server execution. When a client must execute, the server issues a short-lived ticket bound to the actor, thread, attempt, toolCall, operation, and a parameter digest. The client claims admission while online, executes, and the receipt is deduplicated by the original operation. An unsettled disconnect records unknown. A pure display component can replay. A client side effect with no verifiable receipt never resumes as safely done. A remote Agent's internal actions are recorded only at observable boundaries; the system does not claim control over its process. Make "stop requested between two tools, first result saved, second tool not executed" an adapted test, and also verify parallel calls, cancellation, and late results. Model generation and dispatched tools use separate cancellation domains. A stop first closes new tool admission, then stops model generation, and the in-flight tool's promise and persistence tasks keep settling. A timeout or a broken connection records unknown. If the SDK's cancel swallows results, keep an independent result task in the wrapper and end the old loop with an internal pause reason. Any necessary patch targets only that joint and stays on a locked version. This test is implementation acceptance of controllable execution, not a work package waiting on a design conclusion.

6. **Connect the real document chain and close the creation holes.** Following [the existing Notion integration guide](../../docs/plugins/notion.md), enable the connector, configure the callback URL, complete the personal OAuth, refresh the tools, and grant the Bot the exact tools. Check the refreshed write tools against the classification in [catalogue.ts](../../server/src/plugins/catalogue.ts). An unchecked new tool is not auto-granted. The main operation is fixed: read the target page, update the dedicated compatibility follow-up area, then read again to verify. Build the parameters from the schema actually discovered. Where the result is read back directly, use synchronous completion semantics. When the target returns an async task handle, wait for the terminal state. `accepted` is not a write success. The Notion tool capabilities were checked against the official MCP documentation through a Context7 lookup, but the account, authorization, and live behavior are still confirmed by this segment's live test. The creation chain gains a request ID persisted by the confirmation card, in [bot-tools.tsx](../../app/src/lib/copilot/bot-tools.tsx), [agents/routes.ts](../../server/src/agents/routes.ts), and [profile-store.ts](../../server/src/agents/profile-store.ts). Actor plus request ID is unique. The Bot and the deduplication record are written in one transaction, and the same key with different content returns a conflict. Inject a partial grant failure into [app-access.ts](../../server/src/plugins/route-groups/app-access.ts). Re-read from the confirmed refs and fill only the missing items. Do not end early on the application-level granted flag, and do not widen the grant.

7. **Keep records that later work will actually use.** During runs, save the trigger source, run, attempt, and operation references, start and end times, model and tool usage when the provider returns it, artifact references, and failure reasons. Test material goes into `tests/fixtures/aooo/` in this repository, and the expected facts are hand-checked. Record only what is needed. Secrets and credentials never enter the trail. Later questions use these real records, and no parallel evidence system is built.

### Acceptance

- With the Intelligence configuration cleared, local mode starts, and one real model completes the material read, the Notion update, the read-back, and delivers an artifact link. A new thread's history comes from the local database.
- Close the browser mid-run and reopen the same thread. While the service lives, the work continues and the completed result is visible, with no second tool write. After a normal service restart the history is readable. A crash mid-run clearly shows an interrupt, and this segment does not pretend auto-recovery.
- A caller who is not logged in, a wrong user, and a thread the caller cannot access despite Bot access are all refused for read, run, and stop. A duplicate old submission opens no second run. An old stop does not affect a new attempt.
- A creation submitted with the response lost, retried, still yields one Bot. A mid-way grant failure only fills the confirmed missing items. A model's half-finished parameters never execute. Tool results and calls are saved in pairs.
- Focused tests for the tool boundary, input deduplication, reconnect, and creation. Run root `bun run typecheck`. The desktop dev shell connects to this local mode. Packaging acceptance is not in this segment.

## 2. Keep one duty moving

### Segment goal

Without the user opening the page, the Bot follows the same target on a schedule and on GitHub events, and the second pass only fills in the new changes. Duplicate events, duplicate claims, and chat-versus-background races never let two executors advance the same thread.

### Implementation steps

1. **Wire the background entry into the same coordinator.** Replace the cloud runner and client in [the background assembly of index.ts](../../server/src/index.ts), injecting the local history and run services through the narrow interface of [run-turn.ts](../../toolkit/src/run-turn.ts). Change the current order of read history, build the Agent, then take the lock, into the coordinator takes the right, reads the authoritative history, then builds this input. TurnRunner and the coordinator no longer each take the same non-reentrant lock. Keep the queue's own lease: it manages work-item claiming, while the local thread execution right manages the execution context. Callers use one responsibility point for acquiring execution rights.

2. **Decide where one duty's progress lives.** The [routine sweep](../../server/src/routines/sweep.ts) keeps discovering due items, claiming, and dispatching. One fixed Responsibility stores the follow-up target, the target page ID, the processed sources, the material cutoff point, the artifacts, and the open items. Events and schedules both enter that duty. The [responsibility wiring](../../server/src/responsibilities/wiring.ts) assembles the input, and progress is saved through the existing `report_responsibility_progress/recordProgress`. A source is marked processed only after the Notion write is confirmed by a read-back. An unknown result goes to verification first. A Routine remains a schedule, not a second place where document progress is kept. Ordinary standalone Routines keep their existing capability. Every actual execution links the business run, Bot, thread, and local run, and the result returns to the original channel.

3. **Attach schedules to existing duties, then enable real events.** The event source already supports `schedule`, but a Routine is not yet linked to a Responsibility. Add an optional `responsibilityId` to the Routine schema, store, input, and context. On create or edit, check that owner, Bot, and channel agree. Let the duty subscribe to `{source: schedule, eventType: routine.due}`.

   In `server/src/routines/runner.ts`, after the existing pause and ownership checks, a linked Routine calls ingest directly. Fix the externalId to `routine-run:<routineRunId>` and store the routineId and runId in the payload. The model does not decide dispatch. The existing ingest deduplicates by owner, source, and externalId, and the original responsibility queue consumes it. A Routine success only means the event was dispatched. Whether the work finished follows the linked Responsibility run. Ordinary Routines keep using the local Agent, with their own regression test. Accept the main scenario on a short-period Routine, then restore the normal frequency. A missed schedule window follows the existing Routine rules, and history is not replayed for every missed time.

   GitHub events follow the entry in [trigger-routes.ts](../../server/src/responsibilities/trigger-routes.ts). Bind an acceptance repository the user controls, register the trigger and the duty, then configure a reachable callback URL and secret. Open an Issue containing compatibility-change material in the real repository to fire the event. Keep the raw-body signature, the repository binding, the server-side owner resolution, and the delivery deduplication into the queue. The same request reuses the original business run. A body hash cannot guarantee merging all semantically similar events.

4. **Make thread races and the shared document distinct.** Follow the offer, claim, renew, and finish flow of [work/queue.ts](../../server/src/work/queue.ts). Every run-state change carries the current execution generation. After a lease is lost, tool start is stopped, and an old work item cannot settle a new holder's result. In the main scenario, the project-tracking Bot alone writes the target area, and the assessment Bot only returns advice. Different threads may still edit the same external page; the thread lock does not promise to solve concurrent external edits. Read the target area back before every write. If the content has drifted, judge again, and never paper over a conflict with a full-page overwrite.

### Acceptance

- The first material batch forms the first document. The second batch, triggered by schedule, enters the original page: the new changes land, the old content and sources stay, and duplicate sources create no duplicate entries. With the page closed, the worker still finishes the work. One routineRun retry dispatches the duty once. A source that arrives by schedule first and by GitHub later does not write twice, and the reverse order holds too.
- One real GitHub event produces a duty run and updates the original document. The same signed request redelivered does not dispatch twice. A wrong signature, a wrong repository, and a paused duty start no work.

The outcome attaches to the original operation, and then the system completes the result, retries under the current authorization, or stops. A retry click never defaults to performing the unknown write a second time. On recovery, a new attempt reuses the original operation's result. A new model proposing the same parameters is not automatically treated as the original operation: judge by the original call and business-action identity, and never delete a legitimate repeated operation by parameter hash.

4. **Handle lost rights and late results.** An executor outside the current generation cannot update the current run's state or issue new actions, but a real external result returned by an old request is never discarded. The current recovering transaction merges it into one canonical result event, and a conflicting receipt goes to verification. An old executor can only submit the original operation's receipt. It cannot write current history or terminal state, or re-acquire the execution right. The dispatch flag commits before the actual call. A crash between the two also conservatively records unknown, and a probably-not-sent state never justifies an automatic retry. A request without a definite result stays unknown. 5. **Use the recovery records for real diagnosis.** Let the existing conversation and audit views link the trigger, queue item, business run, attempt, operation, wait, and artifact, without building a monitoring platform.
